# RadiusDesk – Analyse du Time Limit

## 1. Cartographie des profils RADIUS
- **Modèle de données.** `Profiles` est relié aux composants via `Radusergroups` : chaque profil créé par l’éditeur « simple/advanced » génère un groupname `SimpleAdd_<profileId>` (ou un composant FUP) et l’associe à `Radgroupcheck`/`Radgroupreply` (`src/Controller/ProfilesController.php:360`, `src/Controller/ProfilesController.php:980`). Les tables clés : `profiles`, `profile_components`, `radusergroup`, `radgroupcheck`, `radgroupreply`, `profile_fup_components` (schéma `setup/db/rd.sql:5268`).
- **Attributs RADIUS générés.** `_doRadius()` construit les attributs standards : `Rd-Reset-Type-Data`, `Rd-Total-Data`, `Rd-Cap-Type-Data`, `Rd-Mac-Counter-Data`, `Rd-Reset-Type-Time`, `Rd-Total-Time`, `Rd-Cap-Type-Time`, `Rd-Mac-Counter-Time`, les limites de sessions (`Simultaneous-Use`), la QoS (`Mikrotik-Rate-Limit`, `WISPr-Bandwidth`) et les limites avancées jour/mois (`src/Controller/ProfilesController.php:980`). Le flag `time_cap_type` devient `Rd-Cap-Type-Time` (`hard` ou `soft`).
- **Comportements FreeRADIUS.** `FreeRadiusBehavior` alimente automatiquement `radcheck/radreply` lorsque des `vouchers`, `permanent_users` ou `devices` sont créés/modifiés (`src/Model/Behavior/FreeRadiusBehavior.php:22-120`). Pour les vouchers, `time_valid` est converti en chaîne `dd-hh-mm-ss` et synchro avec `Rd-Voucher`; `time_cap` est recalculé en secondes (`src/Model/Behavior/FreeRadiusBehavior.php:390-410`).
- **Résolution des profils lors de l’inscription.** Les contrôleurs `VouchersController`, `PermanentUsersController`, `DevicesController` résolvent `profile_id` vers `profile` pour injecter l’attribut `User-Profile` dans `radcheck` et les `Radusergroups` (ex. `src/Controller/VouchersController.php:294-356`).
- **Composant FUP.** `_doRadiusFup()` supprime/recrée les attributs `Rd-Fup-Bw-Up/Down`, `Rd-Fup-Burst-*`, `Rd-Fup-Comp-Count`, `Rd-Fup-Profile-Id`, `Rd-Fup-Ip-Pool`, `Rd-Fup-Vlan` selon l’éditeur FUP (`src/Controller/ProfilesController.php:821`).

## 2. Accounting & Activity Monitor
1. **Collecte RADIUS.** FreeRADIUS (module sql) écrit dans `radacct`. Les triggers `manage_user_stats_*` (`setup/db/mysql_sharding/9.002_adjust_radacct_triggers.sql:1-210`) alimentent `user_stats` (création de tranches de 30 min) et dupliquent les sessions terminées dans `radacct_history` quand `acctstoptime` passe de `NULL` à une valeur (`setup/db/mysql_sharding/9.002_adjust_radacct_triggers.sql:210-235`).
2. **File d’attente new_accountings.** La policy `RADIUSdesk_async_acct` insère `username/mac` dans `new_accountings` à chaque event Accounting (`setup/radius/freeradius/3.0/policy.d/radiusdesk:1192-1245`, table définie `setup/db/rd.sql:3586`).
3. **Cron `bin/cake accounting`.** `AccountingShell` dépile `new_accountings`, détecte le type (`Rd-User-Type`) et recharge les compteurs via `CountersTask` (RADIUS → tableau d’attributs) et `UsageTask` (requêtes `user_stats`) pour mettre à jour `vouchers`, `permanent_users`, `devices` et `mac_usages` (`src/Shell/AccountingShell.php:40-276`, `src/Shell/Task/CountersTask.php:9-86`, `src/Shell/Task/UsageTask.php:16-233`). `mac_usages` est créé par la migration `setup/db/8.102_add_mac_usages.sql:1-25`.
4. **Calculs d’usage.** `UsageTask` fournit : `time_usage`, `data_usage`, `time_left_from_login`, `time_left_from_expire`, `perc_used_from_login` via `user_stats` (`src/Shell/Task/UsageTask.php:16-233`).
5. **Tableaux de bord.**
   - **Activity Monitor** appelle `RadacctsFastController@index` pour lister `radacct` (filtre `acctstoptime IS NULL` pour les sessions actives) et effectue la pagination côté SQL (`src/Controller/RadacctsFastController.php:17-98`).
   - **Historique / usage détaillé** passent par `RadacctsController` (peut basculer `workingModel` sur `radacct_history`), et `DataUsagesController`/`DataUsagesNewController` qui agrègent `user_stats` + `user_stats_dailies` pour les graphes.
   - **API usage ponctuel** : `RadacctsController::getUsage` retourne `time_used`, `time_cap`, `data_used`, `data_cap` en priorisant `mac_usages`, sinon les colonnes `*_used` des entités ou, à défaut, les valeurs issues de `CountersComponent` (`src/Controller/RadacctsController.php:33-160`, `src/Controller/Component/CountersComponent.php:9-70`).
6. **Nettoyage.** `CompactingShell` et `UpdateUserStatsShell` sont maintenus pour compatibilité mais leur logique est désormais gérée par les triggers; ils servent de référence historique (`src/Shell/CompactingShell.php:1-70`, `src/Shell/UpdateUserStatsShell.php:1-110`).

## 3. Statuts utilisateurs / vouchers
- **Vouchers.** `vouchers.status` (enum `new/used/depleted/expired`) est alimenté en plusieurs endroits :
  - lors de l’édition, on force `status='new'` pour signaler une modification (`src/Controller/VouchersController.php:560-620`).
  - `AccountingShell` positionne `status='used'` quand une consommation est détectée, et `depleted/expired` quand `time_left_from_login` ou `time_left_from_expire` atteignent zéro (`src/Shell/AccountingShell.php:40-190`).
  - `VoucherShell` (cron ~15 min) recalcule ces statuts même si aucun nouvel accounting n’est arrivé, en s’appuyant sur `UsageTask` (`src/Shell/VoucherShell.php:17-94`).
  - `RadacctsController::_voucher_status_check` remet un voucher à `new` lorsqu’on supprime l’unique session associée (`src/Controller/RadacctsController.php:843-872`).
- **Permanent users / devices.** Le schéma ne prévoit pas d’état `new/used` : on suit `perc_time_used`, `perc_data_used`, `time_used`, `time_cap`, `data_used`, `data_cap`, plus les colonnes `active` et `admin_state` (`DESCRIBE permanent_users`). `AccountingShell` met ces colonnes à jour (ou `mac_usages` dans le cas des compteurs par MAC). L’état commercial reste géré via `admin_state` (active/suspended/expired …) et les attributs `Rd-Account-Disabled`/`Rd-Admin-State` dans `radcheck` (`src/Model/Behavior/FreeRadiusBehavior.php:22-48`).

## 4. FUP (Fair Usage Policy)
- **Déclaration.** Chaque composant FUP (`profile_fup_components`) stocke condition (`day/week/month usage` ou `time_of_day`), seuil `data_amount/data_unit`, action (`block`, `increase_speed`, `decrease_speed`), bande passante cible, IP pool/vlan (`setup/db/rd.sql:5268`). Ils sont liés à un profil par `profile_id`.
- **Provisioning RADIUS.** `_doRadiusFup()` pose les attributs `Rd-Fup-*` dans `radgroupcheck` à chaque sauvegarde de profil. Le compteur `Rd-Fup-Comp-Count` permet à FreeRADIUS de savoir qu’il doit charger la logique perl `pl_fup` (`src/Controller/ProfilesController.php:821`).
- **Application.** `FupShell` scanne les `radacct` actifs, identifie les profils avec composants FUP, calcule l’usage récent via `user_stats` (ou vérifie une plage horaire) et décide si un composant doit être appliqué. Il mémorise la décision dans `applied_fup_components` et déclenche une déconnexion via l’API `/radaccts/kick-active-username` pour forcer la reconnexion et l’application des nouveaux attributs (`src/Shell/FupShell.php:23-260`).

## 5. Déconnexions / kick (hard vs soft)
- **Interface utilisateur.** `RadacctsController::kickActive` et `::kickActiveUsername` exposent les actions « Kick session » ou « Kick user » qui transmettent les `radacctid` à `KickerComponent` (`src/Controller/RadacctsController.php:544-610`).
- **Implémentation multi-NAS.** `KickerComponent` détecte le type de NAS via `dynamic_clients` ou `nas` et applique la méthode appropriée : marque `disconnect_flag` pour AccelRadiusDesk, publie une commande MQTT/MESHdesk, appelle l’API Mikrotik (`RouterOS` client) pour supprimer la session Hotspot/PPPoE, ou envoie un `CoA/PoD` standard (`src/Controller/Component/KickerComponent.php:17-170`, `src/Controller/Component/MikrotikApiComponent.php:12-70`). Les AP Omada/EAP gérés via MESHdesk/APdesk passent par les mêmes hooks `node-actions` ou `ap-actions` (URL internes indiquées dans le composant).
- **Kicks automatiques.** `FupShell` applique la même méthode pour forcer la reconnexion lorsqu’un composant FUP change. Les scripts `voucher`/`accounting` ne kickent pas directement mais peuvent marquer un compte `depleted` ce qui provoque ensuite un rejet RADIUS (soft kick).

## 6. Analyse du Time Limit actuel
- **Stockage du « first login ».** Il n’existe pas de colonne dédiée. Le timestamp initial est implicitement : (a) le plus ancien `user_stats.created` pour `username`/`callingstationid` (utilisé par `UsageTask::time_left_from_login` (`src/Shell/Task/UsageTask.php:186-233`)); (b) le premier `radacct_history.acctstarttime` qui est interrogé directement par FreeRADIUS quand `Rd-Voucher` est actif (`setup/radius/freeradius/3.0/policy.d/radiusdesk:652-688`).
- **Évaluation côté FreeRADIUS.**
  - Les profils simples/avancés posent les attributs `Rd-Total-Time`, `Rd-Reset-Type-Time`, `Rd-Cap-Type-Time`. Lors de l’`authorize`, la policy `RADIUSdesk_time_counter` charge `Rd-Used-Time` depuis `user_stats` (en mode global ou par MAC) puis appelle le module Perl `pl_check_usage_time` qui calcule `Rd-Avail-Time` et rejette si le quota cumulatif est dépassé (`setup/radius/freeradius/3.0/policy.d/radiusdesk:600-648`, `setup/radius/freeradius/3.0/mods-config/perl/check_usage_time.pl:1-45`). Ce mécanisme est strictement **cumulatif** : seule la somme des durées d’activité importe.
  - `Activate upon first login` côté voucher remplit `time_valid` → `Rd-Voucher` et la policy `RADIUSdesk_voucher_check` compare le temps écoulé depuis le premier `radacct_history.acctstarttime` à cette durée. S’il ne reste que X secondes, la policy réduit `Session-Timeout` ou rejette l’authentification (`setup/radius/freeradius/3.0/policy.d/radiusdesk:652-900`, `947-1005`).
- **Pourquoi le comportement semble cumulatif.**
  1. **Profils/Permanent users** n’ont pas de notion de « first login » : aucune colonne/attribut n’est mise à jour pour lancer un compte à rebours. `Rd-Total-Time` reste donc un quota d’usage.
  2. **Vouchers** : `activate_on_login` est piloté par les champs `days_valid/hours_valid/minutes_valid` (cf. interface) mais n’est pas automatiquement synchronisé avec le « Time Limit » du profil. Le profil peut donc imposer 10 h d’usage cumulé tandis que `time_valid` reste vide → `Rd-Voucher` n’est pas créé.
  3. **Chronométrage différé.** `UsageTask::time_left_from_login` exploite `user_stats`, donc tant qu’aucune nouvelle écriture `user_stats` n’arrive (client hors ligne), les scripts `accounting/voucher` ne voient pas que la fenêtre « first login + 10h » est atteinte. Les NAS ne déconnectent que lorsqu’ils reçoivent un rejet RADIUS ou un CoA.
  4. **radacct_history dépend d’un stop.** Si la première session n’a pas encore été clôturée (ex. client toujours en ligne, `acctstoptime NULL`), il n’y a pas encore de ligne dans `radacct_history`, donc `RADIUSdesk_voucher_check` laisse passer jusqu’à ce qu’une mise à jour `acctstoptime` intervienne.
- **Conséquence pour le scénario décrit.** Un profil « 10h hard » appliqué sans `time_valid` se traduit par `Rd-Total-Time=36000`. FreeRADIUS additionne simplement les sessions (`user_stats`) : 3×3h + 1h → rejet à ~10h d’activité, même si l’horloge réelle dépasse largement. Côté interface, cocher `Activate upon first login` sur le voucher ne change rien tant qu’aucune durée `time_valid` n’est saisie ou alignée sur la limite du profil.

## 7. Pistes pour un mode « hard time » basé sur le premier login
1. **Propager `time_valid` automatiquement depuis le profil.**
   - *Principe* : ajouter un champ « Mode de limite » dans l’éditeur de profil (`ProfilesController` + modèle) et, lorsqu’il est réglé sur « hard (first login) », auto-remplir `time_valid` et `Rd-Voucher` pour chaque voucher/permanent user/devices créé sur ce profil. `FreeRadiusBehavior` pourrait calculer `time_valid` à partir de `time_amount/time_unit` si `time_limit_enabled && hard_mode` (`src/Model/Behavior/FreeRadiusBehavior.php`) et ajouter un attribut `Rd-First-Login` stockant la date une fois le premier login détecté via un SQL `INSERT IGNORE` déclenché depuis FreeRADIUS (`policy.d/radiusdesk`).
   - *Fichiers à modifier* : `src/Controller/ProfilesController.php` (formulaire et `_doRadius` pour poser un nouvel attribut p.ex. `Rd-Time-Mode`), `src/Model/Behavior/FreeRadiusBehavior.php` (copie automatique de la durée dans `time_valid`/`Rd-Voucher`), `setup/radius/freeradius/3.0/policy.d/radiusdesk` (définir que `Rd-Time-Mode=hard` ⇒ appeler `RADIUSdesk_voucher_check` même pour les permanent users), éventuellement `radcheck` pour stocker `Rd-First-Login`.
   - *Avantages* : enforcement immédiat via `Session-Timeout` côté NAS (Mikrotik, Omada Hotspot et PPPoE supportent ce reply attribute). Aucun cron supplémentaire.
   - *Inconvénients* : nécessite de propager `Rd-Voucher` vers tous les types d’utilisateurs et de garantir que `radacct_history` contient au moins une ligne (donc dépend encore de la fermeture de la 1re session). Ajouter `Rd-First-Login` lors du premier Accounting Start (UPDATE SQL) simplifierait ce point.

2. **Suivi explicite `first_login_at` / `hard_expire_at` côté base.**
   - *Principe* : nouvelles colonnes `first_login_at`, `hard_expire_at`, `time_mode` sur `vouchers` et `permanent_users`. Lorsqu’un premier événement `new_accountings` survient, `AccountingShell` renseigne ces colonnes (`user_stats` → timestamp). Une tâche cron dédiée (ou `AccountingShell`) détecte les comptes dont `hard_expire_at < NOW()` et : (a) fixe `status='expired'` ou `admin_state='expired'`; (b) invoque `/radaccts/kick-active-username` pour les sessions ouvertes.
   - *Fichiers à ajuster* : migrations SQL, `src/Shell/AccountingShell.php` (étape de saisie des timestamps), `src/Shell/VoucherShell.php` (prise en compte d’un statut `expired` même sans trafic), `src/Controller/RadacctsController.php` (pour afficher l’état « hard expired »).
   - *Avantages* : marche même si le client reste longtemps hors ligne (car la vérification se fait sur une horloge absolue). Facile à auditer/reporting.
   - *Inconvénients* : non temps réel—le rejet RADIUS ne se produit qu’après mise à jour du statut, donc il faut forcer une déconnexion ou rejeter lors du prochain Access-Request via un attribut `Rd-Hard-Expired`. Demande une gestion de concurrence (ne pas écraser `first_login_at` si déjà renseigné).

3. **Double mode cumulatif/hard côté FreeRADIUS.**
   - *Principe* : introduire un nouvel attribut `Rd-Time-Cap-Mode` (valeurs `cumulative`/`window`) placé dans `radgroupcheck`. FreeRADIUS, dans `RADIUSdesk_time_counter`, intercalerait une comparaison différente : si `window`, calculer `time_elapsed = NOW() - first_login` (en récupérant `Rd-First-Login` ou la première `user_stats.created`, ou via une nouvelle table `first_login_audit` alimentée par triggers) et définir `Rd-Avail-Time = limit - time_elapsed`. `pl_check_usage_time` resterait inchangé, mais la policy renseignerait `Rd-Used-Time` différemment. On pourrait conserver le cumulatif en option (utile pour les forfaits 10h consommables sur plusieurs jours).
   - *Fichiers à modifier* : `ProfilesController` pour poser `Rd-Time-Cap-Mode`, `setup/radius/freeradius/3.0/policy.d/radiusdesk` (logique conditionnelle dans `RADIUSdesk_time_counter`), script SQL pour créer une table `first_login_audit` alimentée par un trigger sur `radacct` (`AFTER INSERT` stockant `username`, `groupname`, `acctstarttime` quand aucun enregistrement n’existe encore). Mikrotik/Omada continueraient de recevoir un `Session-Timeout` (hard) ou la valeur cumulée (soft) selon le cas.
   - *Avantages* : choix du mode au niveau du profil sans modifier les entités finales. L’utilisation d’une table `first_login_audit` garantit que même si `radacct_history` n’a pas encore d’entrée (session toujours ouverte), le premier login est connu.
   - *Inconvénients* : complexifie la policy RADIUS (plus de requêtes SQL) et nécessite un mécanisme de purge de la table `first_login_audit` quand un utilisateur est réinitialisé.

Dans les trois scénarios, il faudra s’assurer que le statut (`vouchers.status` ou `permanent_users.admin_state`) reste cohérent avec la coupure effective (kick automatique via `KickerComponent` ou rejet RADIUS) et que la valeur envoyée dans `Session-Timeout` est comprise par les NAS cibles (Mikrotik Hotspot/PPPoE, Omada, Accel…).
